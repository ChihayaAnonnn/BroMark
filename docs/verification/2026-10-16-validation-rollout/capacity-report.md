# 固定到达率诊断：NO-GO

本次不认定安全容量，不宣布性能优化比例。测量的是同一台Apple M4上的隔离双实例诊断；其他ChatSpace服务仍在运行，压测端与服务端共享Docker VM，缺少可比旧语义基线和三个重复。

正式数据：100次/秒，600秒，70%活动查询/10%结果查询/10%兑换/10%抽奖。200个合成用户；次数SKU不限库存；奖品池一次分配100万名额，CREDIT固定1.00，NONE只作耗尽兜底。本档未耗尽奖池。当前配置在首档失败，按停止条件不再升压300/600/1000，也不把重复失败配置当安全容量认证。

14个503在停写快照中均无已提交请求回执，单列于unknown-resolution.json；不把503推断成成功。受理/完成只统计交易订单，不包括读请求或重复轮询。排空时间包括轮询观察延迟；Outbox独立采样的排空时间79.29秒不是业务终态排空时间，两者不能混称精确的全链路清空时刻。

服务端确认与交付耗时使用同一MySQL实例内ACCEPTED→confirmed_at/DELIVERED时间，独立列出，不依赖压测客户端时钟相减。通用collector因缺少运行前应用/DB/压测端校准而保守地将完成与观察延迟字段留空；后测偏差25.08ms、不确定度27.24ms也不满足10ms门限，不能补写成跑前校准通过。

负载过程最初采集的backlog只覆盖Outbox，明确不作为全链路不增长证据。采集器已补充ORDER/OUTBOX/RETRY/BROKER四域并有反例测试；本档结束后完整快照四域均零。新门禁同样拒绝这个旧范围样本，不能用排空后的零掩盖负载期增长。

## 环境与可定位事实

- Apple M4，10核、16GiB；Docker VM10CPU、约7.82GiB。两应用各1CPU/512MiB，JVM Xms128m/Xmx320m。
- JDK25.0.4.1；k6 1.3.0固定digest；MySQL8.0.46，innodb_flush_log_at_trx_commit=1、sync_binlog=1、binlog ON。全局默认隔离RR，业务runner逐事务指定READ COMMITTED。
- MySQL实际max_connections=80；各应用三个逻辑池各8，双实例理论池上限48，预留20，总68低于80。运行配置声明physical limit100，应在真实环境收敛到实际80；本次实际峰值21不等于可以忽略CPU、IO或业务许可限制。
- Rabbit单节点quorum持久队列（副本整体丢失未覆盖）；Redis3主0副本。每实例workflow与notification各8消费者，prefetch16；物理数据库WORKER许可仍只有1，其他工作类别保留独立许可。
- 1000ms轮询的暖机出现明显积压；250ms用于本次正式测量。旧暖机与故障、机器休眠间隙重叠，只保留诊断，不计算性能提升比例。
- 实际线程快照可见多条workflow线程等待同一BoundedDatabaseBudget的WORKER semaphore，另一个线程在账户锁查询；这是业务许可与锁等待方向的证据，不证明单一根因。
- 容器内存接近512MiB，heap_info为DefNew/Tenured布局；未采GC停顿时间，不把尾延迟归因于GC。CPU、连接池、调度与队列应联合定位。

后续实验首先保留回调/查询/恢复配额，按每实例、物理DB和真实80连接上限评估WORKER许可与池大小；再分别验证调度隔离、应用内存/GC和k6预分配VU。每项配置必须单独重跑，不能把这些建议写成已完成优化。恢复处理速率高于持续新增的独立故障实验没有完成，estimatedDrainSeconds留空。

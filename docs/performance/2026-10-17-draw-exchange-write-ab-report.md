# 抽奖、兑换写入 SQL 优化：2 核 4 GiB A/B/A 实验

## 实验结论

代码减少已有账户写入及流水插入 SQL 往返，正确性测试通过，但**未证明成功写入 QPS 或 P99 改善**。首次基线与候选相比，5/100/300 VU 的成功写入 QPS 下降，600 VU 上升；随后同一份基线构建在全新数据上的复测也显著变化。必须保留三轮结果，不能把当前顺序实验用于简历中的 QPS 提升数字。

这版代码作为待性能验收的优化候选保留，未提交；没有将测试通过视作吞吐收益。更低的 SQL 次数是已验证的局部证据，不等于整个服务的容量提升。

## 改动与证据边界

已有账户的加锁路径从每个账户 UPSERT + SELECT FOR UPDATE，改为直接 SELECT FOR UPDATE。缺失账户才执行 UPSERT 并重新读取，保留信用账户先于活动账户、活动 ID 升序的锁顺序。总/月/日三条额度流水从 3 次 INSERT 合并为一次多值 INSERT，校验写入 3 行，收据序列化一次。

抽奖和兑换复用资产仓储；正常已有信用和活动账户时，这两处合计减少 4 次 SQL 往返（账户 2 次、流水 2 次）。共用仓储中的后台发奖、签到路径也会受影响。每个缺失账户的首次创建会增加一次查询。未改变表结构、数据库许可数、幂等复查、资金/额度/订单/Outbox 原子事务和余额条件更新。

未移除服务层独立幂等预查：配置不可用时仍需返回已存在的结果。保留原有 ID 段边界问题；本次观测的 503 未逐条定位，不能都归因于该问题。

## 测试与构建

测试驱动：新增 `AssetWriteEfficiencyV2Test` 在旧实现上失败（已有账户仍有两条初始化 UPSERT）；新实现通过。真实 MySQL 校验已有账户不初始化、单次 INSERT 保留三桶流水、异常回滚后三桶余额及流水不变。既有测试覆盖双实例首次开户、并发幂等与禁用账户。

完整 V2 回归 **248 测试，0 失败、0 错误、0 跳过**；离线 Maven package 成功；独立静态审查无阻断问题。未运行连接外部开发数据库的旧版 SpringBoot 测试。

## 可复现条件

- 单应用实例：Docker `NanoCpus=2000000000`、`memory=4294967296`、`Xmx2g`、replica-count=1。数据库、Redis、RabbitMQ、k6 在应用限额之外，均共享本机 Docker VM。
- TRADE=2、QUERY=1、WORKER=1、CALLBACK=1、RELAY=1、RECOVERY=1，单逻辑数据库连接池 8；限流配置不变。
- 三轮独立全新 200 用户/三库/队列命名空间，账户余额和额度均充足；种子用户名字不同，分片分布可能不同。

## 结论限制与证据

顺序 A/B/A（原基线、候选、相同构建基线复测），每个条件仅一次或两次，没有置信区间；共享宿主机其他服务未停止，结果只代表本机本次实验，不是生产容量或稳定容量保证。closed-loop 输入模型相同但实际请求数会不同。结合写入成功 QPS、P99、受理数量和积压一起判断，不以快速失败的总 QPS 作为收益。

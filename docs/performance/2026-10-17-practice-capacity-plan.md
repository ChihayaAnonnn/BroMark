# 练习项目容量实验

目的：获得固定本地资源下可复现的吞吐、延迟、积压与正确性证据，用于项目分析及简历；不执行生产发布验收。

基准提交：`1aadc89`。复用已构建、已回归的同版本 Java 25 应用，每实例 1 CPU / 512 MiB / Xmx320m，双实例共同处理异步工作，HTTP 负载入口固定为实例 1。MySQL、Redis、Rabbit 与 k6 共享本机 Docker；必须注明该边界，不能声称均衡双实例 HTTP 吞吐或生产容量。

新建专属三库，200 个合成用户，100 万库存，每用户 100 万期初积分及额度。mixed 请求配比为 query/result/exchange/draw = 7/1/1/1，uniform 用户分布。预置结果查询订单与预热请求不进入正式分母。

实验顺序：

1. 60 秒、10 rps 预热。
2. 10 rps × 120 秒原采样/在线查单方式复现。
3. 10 rps × 120 秒轻量采样/结束后 DB 阶段导出方式对照。原始代码、资源和阈值不变；这是观测方式组合对照，不能归因于单独某一采样器。
4. 轻量方式分别测试 query 20/50/100 rps、draw 5/10/20 rps、mixed 20/50/100 rps，各档 180 秒。遇到技术错误、非 2xx、HTTP P99 > 1 秒或交付 P99 > 5 秒时停止该场景升档；后续只在定位后另起独立 run。
5. 有稳定候选时，再选取符合预声明目标的档位执行 600 秒 × 3 次复验；若候选不存在，记录原因，不虚构容量。

练习目标：query/result P99 ≤ 200 ms；draw/exchange 受理 P99 ≤ 500 ms；draw 同库 ACCEPTED→DELIVERED P99 ≤ 5 秒；技术失败率 < 0.1%；实际到达实现且无持续积压。任何被限流档位另列，不称为成功容量。缺失的 dropped_iterations 保留未知，不能补零；需要结合 k6 执行数、请求数与到达时序证明实际负载。

完成耗时只用同库服务端时间差，避免把跨时钟偏差当作业务延迟。停写后核对六域差异、未完订单、待处理任务和待审状态；未发生支付/签到的场景不构成其容量或非零正确性证据。

独立原始目录：`/Users/vivix/Desktop/workspace/BroMark-practice-capacity-20261017`。`private/` 为 0700 的 JWT/密钥/seed 区域，不提交、不纳入公开证据包。结束后保留脚本、请求、k6 summary、采样、数据库阶段、对账、日志及哈希清单。仅清理本轮拥有的应用/临时 Rabbit，数据卷与三库保留；不停止其他项目服务。

## 执行中记录的调整与发现

- 原观测方式与轻量方式都未复现历史 JDBC 提交长尾；本轮 200 用户与历史 20 用户不同，不能称为历史实验的完全同条件复现。
- 查询 100 rps 发生 429，纯抽奖 5 rps 发生 503，mixed 20 rps 发生 503，按预声明停止相应场景升档。draw 10/20、mixed 50/100 因此不执行。
- 两次纯抽奖 503 后增加 60 秒异常 JFR；mixed 阶段再录制 180 秒异常 JFR。诊断动作与时间均保存，不把带额外诊断的失败窗口当成无观测开销的对照。
- JFR 捕获 mixed 的兑换 503 同时刻 `BlockOrderIdGenerator.next → RouteCodec.newEventId → ExchangeService.exchange` 的号段耗尽异常；独立 Java 探针确定性复现该边界。纯抽奖的两个失败与号段边界相关，但没有同请求异常栈，不扩大已确认归因。
- 长时复验候选加入已成功的轻量 mixed 10 rps；候选选择发生在稳定性运行前，原 selector 保留。最高无错误短测 mixed 候选为 10 rps，因此执行 10 rps × 600 秒 × 3 次，量化当前版本的长时表现，而不悄悄修代码或放宽阈值。
- 核查发现稳定性脚本复用原三库与 seed，第二次 `warmup` 使用相同 `pcwarmup:*` requestId，因此其写操作是幂等重放。该窗口不进入正式分母，也不声称完成了新的读写预热；第一轮 600 秒复验包含新实例的冷写入影响。正式 `stable_10_r1/r2/r3` 的请求 ID 分别独立，不受此重复影响。原始请求不改写。
- 外部实验 helper 将请求行 `phase` 固定为 `formal`，包括名为 `warmup` 的目录；分析按独立目录与请求前缀排除两次预热，不依赖该错误标签。此工具局限保留原始字节并显式说明，后续复跑应修正 helper 的标签及预热 requestId。

## 完成状态

实验已完成：10个正式窗口、55509个全局唯一原请求；两轮停写六域对账通过，5701个正式写请求身份核查通过。三轮600秒复验均达到预声明的混合请求级延迟、总体技术失败率及采样积压目标，但每轮仍出现503；写请求单独失败率为0.1389%。已确认的ID号段缺陷保留为后续修复事项，本轮没有修改业务代码或宣称高并发上限。详见 [最终报告](2026-10-17-practice-capacity-report.md)。

# BroMark 当前性能瓶颈综合分析（2026-10-18）

本文汇总 2026-10-17 至 2026-10-18 的容量、限流、连接池、资源、网络路径和 PostgreSQL 对照实验，回答一个问题：**当前 BroMark 的性能瓶颈在哪里，下一步最值得动什么。**

结论先行：

1. **最紧的瓶颈已经不是 CPU、内存或连接池上限，而是异步交付链路的结构性吞吐不足。** 当前链路把一笔抽奖拆成 6 段串行消费（PrepareDraw → ReserveAward → ReservationHeld → ConfirmReservation → ReservationConfirmed → AwardDelivery），由 8 个共享消费线程处理；在 600 VU 下，受理约 **164 draw/s**，而 `AwardDelivery` 只有 **0.8/s**；即使 5 VU 也只有 **7.5/s**，停压后 30 秒约 **9.3/s**。积压不是“排空慢一点”，而是交付服务率比受理低两个数量级。
2. **第二层根因是数据库事务成本，而不是数据库 CPU。** 600 VU 时 `COMMIT` 平均约 **18 ms**，账户/库存 `FOR UPDATE` 平均 **30～42 ms**，单阶段 InnoDB 行锁等待 **476.7 s/2,946 次**，data file + doublewrite + redo 等待合计约 **164 s/阶段**；但 MySQL 平均只用了 **约 2.04 核**，应用 **2.24/8 核**，没有 CPU 节流。瓶颈是行锁、持久化提交和 I/O 等待，不是算力。
3. **连接池是放大器，不是根因。** 600 VU 时两个用户库各 **64/64** 连接，分别有 **65/127** 个等待者，417 次获取超时、1,151 个 HTTP 503；但 2/4/8 核与每库 8→64 的对照证明，单独加池或加核基本不提升吞吐。
4. **入口限流、业务许可和 MySQL 主机端口转发是“历史瓶颈”，已被逐一定位。** 默认限流 + TRADE=2 时约 **220 成功 QPS**；2 核时 CPU 93% 且累计节流 35 秒；`host.docker.internal:13316` 改为 Docker 网络直连 `:3306` 后受理 QPS 约翻倍。现在这三项不是 8 核实验口径下的首要瓶颈，但默认配置口径下仍然是硬上限。
5. **最重要的口径限定：所有高负载实验都关闭了入口限流和数据库许可（Integer.MAX_VALUE），并把连接池提到每库 64。** 当前 V2 集成配置默认仍是 pool 8、TRADE=2、WORKER=1、RELAY=1。因此 1.7k QPS 是“拆掉保护后的数据库/链路天花板”，不是生产容量；默认配置下会先撞许可与连接池。

| [PostgreSQL 8c4g](2026-10-18-postgresql-8c4g-report.md) | 换 PG 引擎 | 1,881（300 VU 回落 1,316） | WAL 刷盘 10.5 ms/次，stock 41.85 ms，交付 3,031/34,390 | 换引擎不够 |

这张表说明两件事：

- **加 CPU、加连接池、加许可都没有把吞吐推上去**。2 核 pool64 是 788，4 核 772，8 核 916；8 核相对 2 核只多约 16%，而 CPU 利用率从 95% 降到 26%。这说明限制不在应用算力。
- **真正把受理推上去的是网络路径**：同一构建、同一负载，仅把 MySQL 从宿主机端口转发改成容器 DNS 直连，600 VU 从 871 提到 1,726（约 2 倍），而 CPU 只从 1.97 核升到 2.24 核。SQL 微基准里 `SELECT 1` 在 64 并发下从约 3.5～3.7 万 QPS 提到约 37～39 万 QPS，说明原来的转发路径是巨大的隐藏延迟源。

但网络路径修复只解决了“受理”。直连组的最终交付数仍是 1,605（含 200 预置），未交付 24,414，待处理任务 42,661。**受理翻倍，交付没有翻倍。**

## 2. 当前瓶颈链

```
200 个 Tomcat HTTP 线程
        │  同步事务：账户/库存 FOR UPDATE + outbox INSERT + COMMIT(fsync)
        ▼
3 个逻辑库 / 1 个物理 MySQL 实例（pool 64×3，实际活跃 145，等待 150+）
        │  行锁等待 476.7 s/阶段；COMMIT 18 ms；data+dblwr+redo 等待 164 s/阶段
        ▼
8 个 workflow 消费线程 ── 6 段串行事件链 ── 单队列、无阶段优先级
        │  WORKER 事务：23 ms（5 VU）→ 276 ms（600 VU）
        ▼
交付 0.8/s（600 VU） / 7.5/s（5 VU） / 26/s（1 VU 预热可跟上）
        │
        ▼
积压：ACCEPTED 18,315 / CANDIDATE_FIXED 4,660 / COMMITTED 514
```

这条链有两个正反馈：

- 前台写入越多 → 行锁和 fsync 等待越长 → 后台事务也从 23 ms 涨到 276 ms → 后台交付更慢 → 积压更多。
- 后台交付越慢 → outbox/队列积压越多 → 后续事件在队列里排队越久 → 即使某段时间数据库空闲，也要先处理早期阶段的历史积压，交付仍然上不来。

## 3. 证据一：受理侧的饱和点

8 核直连组（pool 64、许可关闭、200 用户、单活动单奖、7:1:1:1、closed-loop）：

| VU | 成功 QPS | 写入成功 QPS | 成功 P99 ms | 写入 P99 ms | HTTP 503 | 应用 CPU/8 | Hikari 获取 ms | 池超时 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 5 | 777.0 | 155.3 | 40.8 | 62.3 | 4 | 1.62 | 0.004 | 0 |
| 100 | 1,639.7 | 318.0 | 432.0 | 1,121.9 | 561 | 2.34 | 3.67 | 0 |
| 300 | 1,675.8 | 312.9 | 1,121.5 | 1,433.4 | 1,401 | 2.24 | 67.25 | 524 |
| 600 | 1,725.7 | 326.9 | 1,416.8 | 2,185.5 | 1,151 | 2.24 | 65.05 | 417 |

三个特征：

1. **100 VU 之后基本不再增长**：100→600 VU，成功 QPS 只从 1,640 到 1,726（+5%），P99 从 432 ms 涨到 1,417 ms（3.3 倍），说明已经进入饱和区。
2. **写入吞吐被钉在约 320/s**：抽奖+兑换成功 QPS 在 100/300/600 VU 分别是 318/313/327，几乎不随并发增加；增加的是排队和失败。
3. **503 随并发放大**：4→561→1,401→1,151；日志里能看到 JDBC read timeout、连接池超时、回滚连接已关闭。1 秒 socket 超时没有放宽，所以数据库一慢，503 就跟着涨。

这里的“成功 QPS”包含 202 受理，**不是交付 TPS**。写入 QPS 也只是“受理成功”的抽奖+兑换，不是最终发奖完成。

## 4. 证据二：数据库到底慢在哪

### 4.1 事务服务时间随并发整体劣化

从 `bm_v2_database_transaction_seconds_*` 指标按阶段差分：

| VU | TRADE 均值 | WORKER 均值 | RELAY 均值 | QUERY 均值 | RECOVERY 均值 |
|---:|---:|---:|---:|---:|---:|
| 5 | 7.0 ms | 23.0 ms | 11.5 ms | 1.2 ms | 1.2 ms |
| 100 | 64.2 ms | 173.6 ms | 64.1 ms | 15.8 ms | 42.8 ms |
| 300 | 157.6 ms | 294.6 ms | 180.2 ms | 108.4 ms | 80.6 ms |
| 600 | 159.5 ms | 276.5 ms | 169.0 ms | 105.0 ms | 92.9 ms |

所有 work class 一起劣化 12～87 倍，而 CPU 只有 2 核左右。这不是“应用算不过来”，是**事务在等锁、等提交、等连接**。TRADE 在 600 VU 的平均事务时间 159.5 ms × 987.6 tx/s ≈ **157 个 TRADE 事务在途（含排队）**，超过两个用户库合计 128 个连接，说明大量时间花在排队而不是执行。

### 4.2 600 VU 的 SQL 服务端时间构成

| SQL | 占总服务端时间 | 调用数 | 均值 | 行锁时间 |
|---|---:|---:|---:|---:|
| COMMIT（db01+db02） | 18.8% | 40,068 | 17.8/18.3 ms | 0 |
| `user_credit_account ... FOR UPDATE`（两库） | 14.6% | 16,558 | 36.4/30.8 ms | 446 s |
| `outbox INSERT`（两库） | 12.3% | 15,502 | 30.3/30.4 ms | 约 30 ms |
| `raffle_activity_account_month` UPSERT（两库） | 10.4% | 23,000 | 17.8/16.9 ms | 约 25 ms |
| `user_credit_account` 余额 UPDATE（两库） | 8.0% | 7,812 | 40.8/38.0 ms | 约 7 ms |
| `raffle_activity_account` 查询/更新 | 约 4.4% | 约 31,700 | 3.4～5.8 ms | 约 41 ms |
| 其余（会话设置、幂等、回执、恢复等） | 约 30% | | | |

Top 15 条 SQL 占全部服务端时间的 **69.7%**。两个结论：

- **持久化提交是最大单项**：COMMIT 占 18.8%，均值 18 ms，和 `innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`、`log_bin=ON`、`flush_method=fsync` 的配置一致。
- **账户行锁是最大可优化项**：两条 `user_credit_account FOR UPDATE` 合计 14.6% 服务端时间、446 s 行锁等待，占全部 476.7 s 行锁等待的约 **94%**。库存 `award_stock FOR UPDATE` 在 100 VU 阶段更突出（均值约 180 ms、行锁 63 s），但到 600 VU 被账户锁超过。

### 4.3 存储等待

600 VU 阶段 InnoDB 文件等待增量（多线程累加，不是墙钟）：

| 等待事件 | 次数 | 累计等待 |
|---|---:|---:|
| `innodb_data_file` | 41,533 | 71.5 s |
| `innodb_dblwr_file` | 14,577 | 55.6 s |
| `innodb_log_file` | 55,669 | 37.2 s |
| 合计 | 111,779 | 164.3 s |

同期 `Innodb_row_lock_time` 476.7 s、`Innodb_row_lock_waits` 2,946 次（平均每次约 162 ms）。没有 `Innodb_log_waits`，也没有 SQL digest 丢失，说明不是日志缓冲区不足，而是**行锁 + 落盘延迟**。

### 4.4 三个逻辑库 = 一个物理实例

`V2BudgetProperties` 把 `00/01/02` 三个逻辑库都映射到同一个 `mysql-it` 物理实例；三个 pool 各 64，实际是 **192 个连接打同一个 MySQL**，共享同一个 buffer pool（128 MiB）、同一块盘、同一个 `max_connections`。所以“三库分片”在存储层没有带来并行度，反而让三份流量在同一个实例上互相争 lock/IO。这是当前拓扑的结构性限制，不是连接池参数能解决的。

## 5. 证据三：连接池与线程竞争

600 VU 阶段 per-pool 峰值（各池取阶段内最大值，不是同一时刻）：

| 池 | active 峰值 | pending 峰值 | max |
|---|---:|---:|---:|
| HikariPool-1（control） | 17 | 0 | 64 |
| HikariPool-2（user db01） | 64 | 65 | 64 |
| HikariPool-3（user db02） | 64 | 127 | 64 |

- 两个用户库都已打满 64，control 库只用 17。**总量 145/192 没满，但热池已经满了**；再加总池上限只会把等待从 pool 转移到 MySQL。
- 直连组 600 VU 线程快照：200 个 HTTP 线程中 46 个等 MySQL Socket、154 个等 Hikari；基线（宿主转发）则是 142 个等 Socket、58 个等 Hikari。`RUNNABLE` 下的 `Net.poll` 也是 Socket 等待，不是 CPU 运算。
- 应用只有 8 个 workflow 消费线程，对 200 个 HTTP 线程。Hikari 的等待队列近似按线程数分配，后台拿到的数据库时间份额大约是个位数百分比；这解释了为什么 WORKER 事务从 23 ms 涨到 276 ms、RELAY 从 11.5 ms 涨到 169 ms。

**池大小的实验结论**：2 核 pool 8→64 只从 739 到 788；pool64 在 2/4/8 核分别是 788/772/916；8 核时 Hikari 获取仍是 105 ms、116 次超时。加池不解决 DB 服务率，只是把排队位置换了个地方。

## 6. 证据四：异步交付链路才是最终限制

### 6.1 每笔抽奖要经过 6 段消费

`EventRouting` 定义的抽奖链路：

```
PrepareDraw → ReserveAward → ReservationHeld → ConfirmReservation
→ ReservationConfirmed → AwardDelivery
```

每段是一个独立 Rabbit 消息、独立 `ConsumerUnitOfWork` 事务。抽奖之外，兑换是 1 段 `ExchangeCompleted`（notifications 队列）。600 VU 时抽奖+兑换各约 163/s，按链路估算需要的消费事务率：

```
required ≈ 163.8 × 6 + 163.1 × 1 ≈ 1,146 tx/s
```

实际 WORKER 事务只有 **17.7/s**，差约 **65 倍**。

### 6.2 8 个线程被 6 段链路摊薄

8 个消费线程、每段一个事务，稳态下每段可用服务率近似：

```
per_stage ≈ workerConcurrency / (stages × mean_worker_tx)
```

| VU | 抽奖受理/s | 需要消费 tx/s | WORKER 实际 tx/s | WORKER 均值 | 每段可用（估算） | PrepareDraw 完成/s | AwardDelivery 发布完成/s |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 5 | 77.6 | 543 | 162.2 | 23.0 ms | 58/s | 41.2 | 7.5 |
| 100 | 159.4 | 1,115 | 34.1 | 173.6 ms | 7.7/s | 8.7 | 1.5 |
| 300 | 157.0 | 1,098 | 19.7 | 294.6 ms | 4.5/s | 5.4 | 0.8 |
| 600 | 163.8 | 1,146 | 17.7 | 276.5 ms | 4.8/s | 4.5 | 0.8 |

这张表的一阶含义是：即使按所有段平均 276 ms 计算，8 线程也只能提供约 4.8/s/段；`PrepareDraw` 实测 4.5/s 与估算接近，说明**“8 线程 ÷ 6 段”解释了第一段和总体量级**。`AwardDelivery` 只有 0.8/s，低于这个上限，原因是交付段事务更重（账户加锁、积分流水、订单更新），且排在 6 段链尾，容易被前面的事件挤占。两者需要分别优化：前者是并发/分段，后者是单事务成本和队列位置。

### 6.3 累计交付：预热能跟上，正式负载立刻掉队

从 `bm_v2_relay_count_total{action="completed",event_type="AwardDelivery"}` 的累计值：

| 时点 | 累计 AwardDelivery | 本段增量/速率 | 同期 PrepareDraw 增量/速率 |
|---|---:|---:|---:|
| 预置 200 + 20 s 预热 518（1 VU） | 718 | 预热 518/20 s ≈ 26/s | 718（含预置） |
| 5 VU 结束 | 1,066 | +348 / 46.5 s ≈ **7.5/s** | +1,914 / 46.5 s ≈ 41.2/s |
| 100 VU 结束 | 1,162 | +69 / 47.2 s ≈ **1.5/s** | +410 / 47.2 s ≈ 8.7/s |
| 300 VU 结束 | 1,223 | +36 / 48 s ≈ **0.75/s** | +260 / 48 s ≈ 5.4/s |
| 600 VU 结束 | 1,309 | +38 / 48.2 s ≈ **0.8/s** | +218 / 48.2 s ≈ 4.5/s |
| 停压后 31 s 排空 | 1,598 | +289 / 31 s ≈ **9.3/s** | +3,314 / 31 s ≈ 107/s |
| 停应用后最终状态 | 1,605 | — | — |

三个关键读法：

1. **1 VU 预热时交付能跟上 26 draw/s**（预置 200 + 预热 518 全部交付），说明链路本身不是完全坏的。
2. **5 VU（78 draw/s）就开始掉队**，交付只有 7.5/s；不是到 600 VU 才坏。
3. **停压后 relay 能跑到 107 PrepareDraw/s，但交付只有 9.3/s**。这说明 relay 不是最终限制；限制在消费段，尤其是需要跨多段推进、且队列里堆满早期事件的场景。

口径说明：`AwardDelivery` 是 relay 侧 `completed` 计数，表示事件已发布确认，不是数据库里的 `DELIVERED` 状态。本轮最终 `DELIVERED=1,605` 与该计数 1,598 很接近，说明消费端基本能跟上已发布的交付事件，因此这里把它当作交付的代理指标；但它仍不是严格的“完成 TPS”。表中增量只用阶段内首末样本；阶段之间的 2～3 秒空档会有一次约 10～18/s 的小冲刺，未计入负载期速率，避免把空档算进正式阶段。

### 6.4 积压的形态

最终状态（含 200 预置与预热）：

| 状态 | 数量 | 含义 |
|---|---:|---|
| ACCEPTED | 18,315 | 已受理，PrepareDraw 还没消费 |
| CANDIDATE_FIXED | 4,660 | 已定候选，ReserveAward 还没消费 |
| COMMITTED | 514 | 已确认，AwardDelivery 还没消费 |
| DELIVERED | 1,605 | 已交付（含 200 预置） |
| RESULT_RECORDED | 925 | 已记录结果 |

75% 的未完成订单（18,315/24,414）停在第一段 `ACCEPTED`。这不是“最后一公里发奖慢”，而是**第一段消费就没跟上受理**，后面的段数只是把差距继续放大。

按停压后 9.3/s 的观测速率粗算，清掉 24,414 笔未完成订单需要约 **44 分钟**；按 600 VU 负载期的 0.8/s 则要 8 小时以上。30 秒的排空窗口远远不够，所以“最终 DELIVERED 1,605”不能当作交付容量，只能当作“本轮窗口内交付了多少”。

## 7. 证据五：不是 CPU、内存或 GC

| 指标 | 2 核实验 | 8 核实验（MySQL 直连 / PG） | 判断 |
|---|---|---|---|
| 应用 CPU | 93.0%（300 VU）、92.3%（600 VU） | 2.24/8 核 ≈ 28% | 2 核时是共瓶颈；8 核时不是 |
| CPU 节流 | 300 VU 35.1 s、600 VU 22.5 s | 0 个周期 | 2 核时确实被配额限制 |
| 内存 | 峰值约 1,023 MiB / 4 GiB（25%） | 约 964 MiB / 4 GiB | 不是瓶颈 |
| GC | 最大暂停 71 ms | 最大暂停 14 ms（600 VU，MySQL） | 尾延迟有贡献，但不是主因 |
| Full GC / OOM | 0 / 0 | 0 / 0 | 不是瓶颈 |
| PostgreSQL 600 VU | — | 最大 GC 暂停 273 ms | 仍不是主因 |

2 核→4 核→8 核的吞吐是 788→772→916，CPU 利用率 95%→48%→26%。如果 CPU 是主瓶颈，4 核和 8 核应该带来接近线性的提升；实际没有。**8 核实验里“只用了 2.2 核”不是浪费，而是线程都在等数据库。**

## 8. 证据六：换 PostgreSQL 不是银弹

| VU | MySQL 直连成功 QPS | PG 成功 QPS | MySQL P99 | PG P99 | PG 交付状态 |
|---:|---:|---:|---:|---:|---|
| 5 | 777 | 1,619 | 40.8 | 17.0 | — |
| 100 | 1,640 | 2,425 | 432.0 | 259.5 | — |
| 300 | 1,676 | 1,316 | 1,121.5 | 1,621.7 | — |
| 600 | 1,726 | 1,881 | 1,416.8 | 1,299.3 | DELIVERED 3,031 / 34,390 |

PG 在 100 VU 明显更好，但 300 VU 回落到 1,316，600 VU 也只有 1,881，**不是单调提升**。PG 侧同样观察到：

- `award_stock ... FOR UPDATE` 平均约 **41.85 ms**，热点行仍串行；
- WAL 刷盘 4,416 次、累计 46,443 ms，约 **10.52 ms/次**；
- 最终未完成 31,359、待处理任务 52,948，`passed=false`。

这说明**持久化提交和热点行竞争是跨引擎的共性问题**，换引擎只能改变常数，不能改变“6 段链路 + 8 线程 + 单队列”的结构。PG 在 5/100/600 VU 的 P99 更低，但 300 VU 反而更差，且交付仍跟不上受理；不能把“换 PG”当作已消除瓶颈。

## 9. 哪些是“假瓶颈”，哪些是“真瓶颈”

### 9.1 容易误判的项

| 项 | 为什么不是首要瓶颈 | 证据 |
|---|---|---|
| 8 核 CPU 没用满 | 线程在等 DB，不是算力 | 2.24/8 核、0 节流；加核 772→916 |
| 内存 4 GiB 不够 | 峰值 <1.1 GiB，无 OOM/Full GC | memory.events 全 0 |
| 连接池 64 不够 | 加到 64 后热池满、等待 127，但总活跃 145/192；再加只是转移排队 | per-pool 64/64，pending 65/127 |
| SQL 往返太多 | 减少 4 次往返的 A/B 没有证明 QPS 收益 | write AB 三轮漂移大于收益 |
| MySQL 引擎不行 | PG 也积压，WAL/stock 仍慢 | PG 交付 3,031/34,390 |
| 网络仍是主因 | 直连已把受理翻倍；剩余等待在 DB 内部 | 账户锁 36 ms、COMMIT 18 ms |
| 异步 relay 发布太慢 | 停压后 relay 可到 107/s，交付仍 9.3/s | 累计事件表 |

### 9.2 工作量形态带来的“假热点”

必须明确：这批实验是 **200 用户、单活动、单奖、100% 命中积分奖**。

- 600 VU / 200 用户 ≈ 每个用户 3 个并发 VU，`user_credit_account FOR UPDATE` 的 446 s 行锁等待很大程度是**同一用户被并发抽奖**造成的；真实用户通常不会同时发 3 个抽奖请求。这一项在真实流量下会显著下降。
- 单活动、单奖、100% 命中，使 `award_stock` 的同一行被所有抽奖串行化；这是**真实可能存在**的热点（爆款活动），但当前实验把它放大了。
- 所以：**账户行锁要先换用真实用户基数复测，再决定是否优化；库存热点可以先按真实爆款场景优化。**

## 10. 瓶颈排序

按“对端到端交付的影响 × 证据强度”排序：

| 优先级 | 瓶颈 | 证据 | 影响 | 置信度 |
|---|---|---|---|---|
| **P0** | 异步交付链路：6 段串行 + 8 共享线程 + 单队列 | PrepareDraw 4.5～41/s，AwardDelivery 0.8～7.5/s；公式解释第一段量级 | 决定最终交付容量；积压主因 | 高 |
| **P1** | 数据库持久化提交与热点行锁 | COMMIT 18 ms、行锁 476.7 s、InnoDB 164 s、stock 42 ms | 把 WORKER 事务从 23 ms 拉长到 276 ms | 高（延迟）/ 中（锁 vs IO 占比） |
| **P2** | 前后台共享连接池、无优先级 | 200 HTTP vs 8 worker；热池 64/64、pending 127；503 1,151 | 后台拿不到 DB 时间，交付被前台挤死 | 高 |
| **P3** | 受理路径同步写放大 | outbox INSERT 12.3%、quota upsert 10.4%、余额 UPDATE 8% | 拉长前台事务，间接加剧 P1/P2 | 中 |
| **P4** | 默认配置的入口限流/许可/pool 8 | 默认口径约 220 成功 QPS、TRADE 等待 438 ms、41k 429 | 默认配置先撞这里，不是 DB | 高（默认口径） |
| **P5** | ID 号段边界 / 503 / 1 秒 socket 超时 | ID block empty 已确定性复现；503 未逐条归因 | 错误率与重试放大，非吞吐主因 | 高（正确性） |

**一句话**：在放宽保护的实验口径下，P0 是交付链路结构，P1/P2 是它的数据库根因；在默认生产口径下，P4 会先出现，但它只是把 P0/P1 的容量问题提前暴露，不是另一个独立问题。

## 11. 下一步最值得做的实验

按性价比排序。所有实验都建议固定同一阶段、交错重复 3 次，不要再用“顺序单轮 A/B”判断小差异。

### 实验 1：消费并发与分段隔离（最高优先）

- **变量**：`bm.v2.budget.worker-concurrency` 8 → 16/24/32；或把 workflow 队列按阶段拆成 2～3 个队列/消费者池；`prefetch` 16 → 8/32。
- **固定**：8C4G、pool 64、无限许可、100 VU（或 300 VU）单阶段 45 s。
- **观察**：AwardDelivery/s、每段消费延迟、积压斜率、WORKER 事务均值、P99、503、Rabbit ready/unacked。
- **判据**：交付速率是否随并发近似线性上升，直到 WORKER 事务均值开始恶化；如果 24 线程仍不升，说明瓶颈在 DB 而不是线程。
- **预期（待验证）**：如果“8 线程 ÷ 6 段”是主因，提高并发应能把交付从个位数/s 提到 30～50/s；但会加剧 DB 争用，需要与实验 2 一起做。若 24 线程仍不升，则瓶颈在 DB 服务率而不是线程数。

### 实验 2：给后台链路独立的 DB 预算/连接

- **变量**：为 WORKER/RELAY 预留 4～8 个连接或独立小池；或给后台事务更高优先级；前台 HTTP 池相应缩小。
- **观察**：后台 WORKER 事务均值是否从 276 ms 回到接近 23 ms；前台 QPS/P99 的代价；503 是否下降。
- **判据**：交付速率提升 > 前台吞吐下降，才值得。
- **注意**：不是简单把 `WORKER=1` 改成很大；要在物理连接预算内做隔离，避免把 MySQL 打爆。

### 实验 3：合并链路阶段

- **变量**：把 6 段合并为 3 段，例如 PrepareDraw+ReserveAward、ReservationHeld+ConfirmReservation、ReservationConfirmed+AwardDelivery；或把同一订单的相邻事件放在一个消费事务里。
- **观察**：每单消费事务数、交付速率、事务均值、锁等待、失败回滚率。
- **判据**：事务数减半且交付速率提升；注意事务变大后的锁持有时间和回滚成本。
- **风险**：改变状态机与恢复语义，必须先补正确性/故障测试。

### 实验 4：真实基数压测

- **变量**：200 用户/1 活动/1 奖 → 2,000 用户/10 活动/10 奖（保持 7:1:1:1 与总写入速率）。
- **观察**：账户行锁等待、stock 行锁等待、P99、交付速率。
- **判据**：如果账户锁等待大幅下降、交付上升，说明前面的账户锁是实验形态造成的；如果 stock 仍是瓶颈，则优先做库存分桶/原子扣减。

### 实验 5：库存热点专项

- **变量**：单奖 100% 命中 → 10 奖均匀；或单 stock row → 分桶（如 16 桶）+ 原子条件更新。
- **观察**：`award_stock FOR UPDATE` 均值/行锁时间、draw P99、超卖/少卖为 0。
- **判据**：stock 等待下降且对账无差异；这是少数可以独立于异步链路优化的 DB 热点。

### 实验 6：提交/存储专项

- **变量**：buffer pool 128 MiB → 1 GiB；redo/数据文件放独立卷；只测存储，不关闭 `fsync`/`sync_binlog`。
- **观察**：COMMIT 均值/P99、InnoDB data/dblwr/log 等待、每秒提交数。
- **判据**：COMMIT 从 18 ms 降到个位数，才值得继续投入；不要用关闭持久化换吞吐。

### 实验 7：错误与 ID 修复

- **变量**：修复 `BlockOrderIdGenerator` 的“预取返回→最后一个订单 ID→事件 ID 耗尽”边界；对 503 做逐条归因（ID / pool timeout / JDBC read timeout / 业务冲突）。
- **观察**：503 分类计数、技术失败率、重试放大。
- **判据**：不把 ID 缺陷混入容量结论；修复后再重跑同一阶段，确认 503 下降不是靠放宽超时。

## 12. 结论边界

这份分析能支持的和不能支持的：

**能支持：**

- 当前 8 核实验口径下，应用 CPU、内存、GC 不是主瓶颈；数据库事务/锁/持久化和异步交付链路是。
- 连接池从 8 加到 64、CPU 从 2 加到 8，单独都不能提升吞吐；网络直连能提升受理但不能提升交付。
- 交付链路在 5 VU 就已经跟不上，600 VU 时交付/受理差约两个数量级；这是结构性的，不是单次抖动。
- 默认配置（限流+许可+pool 8）下的容量远低于 1.7k QPS，不能把实验值写成生产容量。

**不能支持：**

- “BroMark 支持 1.7k QPS 业务吞吐”——1.7k 是受理，不是交付；最终交付只有 1,605/26,019。
- “瓶颈一定是某个具体 SQL/某把锁”——600 VU 的行锁 94% 在账户行，但那是 200 用户/3 并发 VU 的形态造成的；库存热点更可信，账户锁需要真实基数复测。
- “换 PG 就能解决”——PG 在 300 VU 回落，交付仍积压，WAL/stock 仍慢。
- “加机器/加连接池就能线性扩展”——2/4/8 核与 pool 8/64 的对照已经否定了这一点。
- “最终 DELIVERED 1,605 是稳定交付容量”——它被 30 s 排空窗口截断，且包含 200 预置；应按负载期事件速率和积压斜率判断。

**实验方法限制：**

- 顺序单轮 A/B、共享 10 核 VM、closed-loop 无固定到达率、阶段间继承积压；没有重复试验和置信区间。
- 高负载轮关闭了入口限流和数据库许可，pool 提到 64；与默认配置不是同一口径。
- 工作负载是 200 用户、单活动、单奖、100% 积分奖；账户锁/库存锁的占比受此影响。
- 8c4g 轮没有 Rabbit 队列深度采样；队列增长证据来自 qps-2c4g 轮（workflow ready 1,857→11,939）。
- SQL 服务端时间来自 `performance_schema` 摘要，和 JDBC 客户端往返、HTTP P99 不是同一口径，不能直接相减当网络耗时。

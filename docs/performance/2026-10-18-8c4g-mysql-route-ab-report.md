# 8 核 4 GiB：MySQL 连接路径与数据库等待对照

本轮已定位并验证一项连接路径优化：应用原先通过 `host.docker.internal:13316` 绕经宿主机端口访问 MySQL；改成应用加入 MySQL 所在 Docker 网络，直接访问同一实例的容器 DNS `:3306`。接口受理吞吐明显提升，但本轮最终交付数没有增加，尚未证明异步交付容量改善，不能将该结果写成“整个系统容量翻倍”。

## 为什么只有约 2 核在工作

实际 Docker 配额及 cgroup 均核验为 8 核、4 GiB，未发现 2 核资源配额。HTTP 使用同步 Tomcat 工作线程；基线 300 并发的线程快照中，200 个 HTTP 工作线程有 142 个等待 MySQL Socket、58 个等待 Hikari 连接。`RUNNABLE` 下的 `Net.poll` 也是 Socket 等待，不能当作 CPU 运算。`v2ApiExecutor` 的两个线程并非 HTTP 调用入口，盲目增大它不能解决此现象。

链路表现为：数据库往返/事务等待 → 连接持有更久 → 连接池排队 → HTTP 工作线程阻塞。直连后高负载应用仍只有约 2.24 核在工作，结合线程快照、连接获取和 SQL 等待证据，数据库等待仍是重要约束，8 核不等于必须消耗满 8 核。

## 对照条件

- 两组使用完全相同、只读挂载的应用构建；生产类 SHA 一致。该构建来自此前 251 项 V2 测试通过的产物，本轮没有修改 Java 业务代码，也没有重新执行这 251 项测试。
- 应用均为 8 核、4 GiB、`-Xmx2g`；3 个 Hikari 池各 64；MySQL 实例相同，测试期间连接数上限均为 300，结束恢复为 80。
- 均关闭测试模式的入口 RPS、入口并发和数据库业务许可限制；认证、事务、业务约束、连接池、1 秒 JDBC Socket 超时、后台执行器保留。
- 200 个用户、相同开账额度、各自全新三库，先预置 200 个已交付订单；1 VU 暖机 20 秒。正式阶段 5/100/300/600 VU 各 45 秒，无 sleep、无固定 RPS，7 查询 : 1 查单 : 1 兑换 : 1 抽奖。
- 唯一性能条件变化：MySQL 的宿主机转发路径改为 Docker 网络直连。额外网络接入也属于此部署配置变化。两组最终清理、恢复依赖初始停止状态。
- 顺序单轮 A/B、共享宿主，阶段间继承各自积压；闭环 VU 相同，实际发送量不同。不能视为多轮统计保证或持续到达率下的容量上限。CPU 采样窗口包含容器启动/尾部轮询，具体秒数保留在 comparison.json；QPS 使用 k6 自身 rate。

## SQL 路径证据与剩余瓶颈

独立 JDBC `SELECT 1` 探针使用同一 MySQL UUID、相同客户端、复用连接，1/16/64 并发，宿主机/直连/直连/宿主机 ABBA 顺序，每点 4 秒。64 并发下宿主机路径约 34,788～37,468 QPS，直连约 372,341～389,359 QPS，全部零错误。该微基准只证明传输路径差异，不能将十倍差异直接推广为业务收益；其 P99 是每十次抽样的口径。

在完整业务 600 VU 阶段，账户 `SELECT STATUS … FOR UPDATE` 服务端均值由两库约 60.66/61.35 ms 降为约 36.42/30.83 ms；`COMMIT` 服务端均值仍约 17.84/18.28 ms。P_S 摘要服务端时间和 JDBC 客户端往返时间口径不同，不能直接相减当作纯网络耗时。

直连组 600 VU 的全局 InnoDB 文件等待增量：redo log 约 37.20 秒、data file 约 71.50 秒、doublewrite 约 55.61 秒。这些是多个线程累加的等待时间，可能超过阶段墙钟时间，且是共享 MySQL 全局口径。同期累计行锁等待约 476.71 秒/2,946 次，采样最多 19 个目标库行锁等待者；没有 InnoDB log buffer wait，也没有 SQL digest 丢失。结合 COMMIT/账户锁等待和线程栈，剩余主要等待集中于数据库事务、锁与存储 I/O，不能仅靠增加应用 CPU 或连接数解决。

本轮保留事务持久性配置，未通过关闭 fsync 或放宽事务语义制造吞吐。结束后实际读取 MySQL 配置：`innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`、`log_bin=ON`、`flush_method=fsync`、buffer pool 为 128 MiB。缓存容量是否不足需要补充缓存未命中与物理读取证据，本轮未将其认定为已验证根因。后台交付路径仍需独立验证和优化；本轮并未证明其具体某个阶段单独决定全部交付上限。
